# NinjaTerm Manual

## Getting Started

Welcome to **NinjaTerm** - an embedded developer's terminal that's got your back!

NinjaTerm is an open source and free electron (or web-based) application designed for viewing debug data and sending commands when developing firmware for an embedded device (e.g. microcontroller). Connect via serial port, TCP socket, Bluetooth LE, or SEGGER RTT.

If you are looking for a serious terminal for continual use, the installable desktop versions are recommended. If you are looking for a quick way to view some serial data without having to install anything, the web-based version is for you!

## Installation Options

### Desktop Application

For the best experience, download and install the desktop application.

For the most up-to-date version, go to the NinjaTerm [homepage](https://ninjaterm.mbedded.ninja).

For previous versions:

1. Go to the [NinjaTerm releases page](https://github.com/gbmhunter/NinjaTerm/releases)
2. Download the appropriate version for your operating system:
   - **Windows**: Download the `.exe` installer
   - **macOS**: Download the `.dmg` file
   - **Linux**: Download the `.AppImage` or `.deb` package
3. Install and run the application

### Web-Based Version (Quick Start)

The fastest way to get started is to use the web-based version:

1. Visit [https://ninjaterm.mbedded.ninja/app](https://ninjaterm.mbedded.ninja/app)
2. Connect your serial device
3. Start using NinjaTerm immediately!

For the web-based version, you'll need:

- **Chrome, Edge, Brave**: Full native support
- **Opera**: Full native support
- **Firefox**: Requires the [WebSerial for Firefox extension](https://addons.mozilla.org/en-US/firefox/addon/webserial-for-firefox/)
- **Safari**: Not supported

## Presets

NinjaTerm has a lot of settings, and for any given device only a handful of them matter. Presets configure that handful for you. Find them in `Settings > Presets`, which is the first entry in the settings list.

| Preset | What it's for |
| --- | --- |
| DOS text-mode (CP437) | Devices that draw menus, frames and borders using the original IBM PC character set — one byte per box-drawing character. Sets CP437 decoding, ANSI escape code parsing, and a DOS font in an 80x25 terminal. |
| Hex dump | Inspecting a binary protocol byte by byte, as zero-padded uppercase hex. |
| Zephyr / RTOS shell | An interactive shell on an embedded target: coloured log levels, line editing, and CR-terminated commands. |
| Plain-text log capture | Leaving a device running and reading back what it printed, with an ISO 8601 timestamp on every line and a large scrollback buffer. |

Applying a preset changes only the settings it covers, and shows you exactly which ones will change before it does anything — which is also the quickest way to learn where the relevant settings live. You can undo a preset immediately after applying it.

### Saving your own presets

**Save current settings as preset...** captures how NinjaTerm is set up right now. You choose what it should cover with a set of checkboxes:

| Covers | What goes in |
| --- | --- |
| Connection settings | The connection type, the address (serial port, BLE device, socket address or RTT device), and the connection parameters |
| RX data handling | How received bytes are decoded and displayed |
| TX / key behaviour | What the Enter, Backspace and Delete keys send |
| Display | Font, terminal size, colours, scrollback |
| Logging, Highlight rules, Macros, Filters, Graphing, General, Drawer layout | As named |

Everything starts ticked, so saving captures your setup whole. Untick whatever shouldn't travel with it — this is what makes one preset different from another. A preset for capturing logs has no business carrying connection settings, while a preset for a particular board is mostly about them.

Ticked categories are saved in full. That includes settings naming something on this machine — the log directory, or a particular debug probe — because if you set logging up for a board, reapplying its preset should put the logs back in the same place. The one thing not saved is the recently-used device list, which is a history rather than a setting.

A preset that covers everything behaves exactly like a saved profile did in earlier versions of NinjaTerm: applying it restores your whole setup, and reconnects to the port it was saved with.

### What happened to profiles?

Profiles and presets used to be two separate things. They are now one, and the difference between them is simply what each one covers. Anything you saved as a profile is still there, listed as a preset covering everything including its serial port, and applying it does exactly what loading it used to.

## Connection Types

NinjaTerm supports the following connection types:

- **Serial port**: This is your standard serial port style connection, which uses your OS drivers to connect to COM ports on Windows and devices such as `/dev/ttyUSB0`, `/dev/ttyACM0`, etc. on Linux and macOS.
- **Socket**: This is a TCP socket connection, which allows you to connect NinjaTerm to a socket server. This is useful for when you want to connect to a remote device over a network. The remote device could be sending out data directly across the socket, or it could be another development computer running `socat` that is forwarding data from a local serial port.
- **Bluetooth LE**: This allows you to stream bi-directional serial data across Bluetooth LE. There is no one official serial protocol across BLE, but there a number of popular ones by various vendors.
- **Segger RTT**: This allows you to stream bi-directional data over Segger's Real Time Transfer (RTT) protocol via a SEGGER J-Link (or J-Link OB) debug probe. Useful for getting shell/log output from embedded firmware at high speed without consuming a UART peripheral.

### Serial Port

The traditional way of using NinjaTerm would be to connect to a local serial port. Most modern computers will not have actual physical serial ports, but will use USB to serial adapters to connect to serial devices. NinjaTerm does not know or care, as they show up as normal serial ports in the operating system. These are `COM` ports on Windows, and `/dev/ttyUSB0`, `/dev/ttyACM0`, etc. on Linux and macOS.

### Socket

NinjaTerm allows you to connect to a TCP socket server, which can be useful for when you want to connect to a remote device over a network. The remote device could be sending out data directly across the socket, or it could be another development computer running `socat` that is forwarding data from a local serial port.

To connect to a socket server, you need to specify the host and port of the socket server. You can do this in the `Connection Configuration` page. For example, if you we connecting to another computer on your local network, you could use something like this:

```
Host: 192.168.1.100
Port: 5000
```

It is more difficult that you would expect to detect when a socket connection is "dropped" (when it's not closed cleanly, e.g. when the ethernet cable is pulled out, or the other side resets without closing the connection first). NinjaTerm makes a best effort to detect this using the node API `socket.setKeepAlive();` function. However, this is not a perfect solution and there are many reports of this keep alive functionality working on some systems but not on others.

```js
socket.setKeepAlive(true, 1000);
```

In my limited testing I have found that it detects a dropped connection in about 10-20 seconds.

Also `socket.setTimeout()` is used to set the timeout to 2 seconds during the connection process. It is not used once connection has been made.

```
socket.setTimeout(2000);
```

### Bluetooth LE (BLE)

NinjaTerm supports connecting to BLE devices. There is no one official serial protocol across BLE, but there a number of popular ones by various vendors. NinjaTerm supports the following protocols:

- Nordic UART Service (NUS)
- Microchip Transparent UART Service
- TI Serial Port Service (SPS)
- u-blox u-connectXpress
- Silicon Labs SPP over BLE

See [BLE Serial on blog.mbedded.ninja](/electronics/communication-protocols/bluetooth/#ble-serial) for more information on these BLE serial protocols and how they work.

Also, NinjaTerm allows you to manually specify the service UUID, and the RX and TX characteristic UUIDs to use for the serial communication. This is useful if you have implemented your own custom protocol.

### Segger RTT

[Segger RTT (Real Time Transfer)](https://www.segger.com/products/debug-probes/j-link/technology/about-real-time-transfer/) is a bi-directional communication channel between a host PC and an embedded target microcontroller via a SEGGER J-Link debug probe. It can be an attractive alternative to a typical UART serial port for logs because it uses the same cable as the programmer/debugger.

To use RTT from NinjaTerm:

1. Install [SEGGER's J-Link software](https://www.segger.com/downloads/jlink/).
2. Connect the J-Link (or dev kit with J-Link OB) to the host PC.
3. In NinjaTerm, open `Settings → Connection Configuration` and pick `Segger RTT` as the connection type.
4. Fill in the target device identifier (e.g. `nRF52832_xxAA`, `STM32F407VG`, `RP2040_M0_0`). The field is an autocomplete — start typing and pick from the suggestions, or type any device name accepted by J-Link Commander's `device` command. Previously-used devices appear under a **Recently used** section at the top.
5. Pick the debug interface (usually `SWD`) and speed (typical values 1000–50000 kHz; 4000 is a good default).
6. Optionally point the **J-Link Commander path** field at `JLink.exe` (Windows) or `JLinkExe` (macOS/Linux). Leave it blank to auto-detect — the **Locate** button searches the standard SEGGER install locations (including versioned `C:\Program Files\SEGGER\JLink_V*` folders produced by the "do not replace" install option) and picks the newest version found.
7. Optionally fill in a specific J-Link probe serial number — only needed if multiple probes are connected.
8. Click **Open**.

Under the hood, NinjaTerm spawns J-Link Commander (`JLink.exe`) with a generated script that sets the interface, speed, and device and then calls `connect`. Once the target is attached, Commander exposes RTT channel 0 on TCP port 19021 as a bidirectional telnet stream; NinjaTerm opens a single TCP client to that port for both RX and TX.

A **J-Link Commander output** pane is shown on the Connection Settings page during a session. It is tailed from Commander's own log file and capped at the last 100 lines, useful for diagnosing target-detection failures (wrong device name, wrong interface, unresponsive target, etc.).

If the probe disappears mid-session (e.g. dev kit unplugged), NinjaTerm detects the loss from the Commander log (`Connection to emulator lost!`), transitions the connection to `CLOSED_BUT_WILL_REOPEN`, and polls every 5 seconds. When the dev kit is plugged back in, the session is automatically restored with a confirmation snackbar. On Windows, before each reconnection attempt NinjaTerm runs a quick `Get-PnpDevice` query for a SEGGER USB device (VID 0x1366) so Commander's interactive "Probe selection" GUI dialog is never triggered while the cable is still out.

NinjaTerm defaults to RTT up/down channel 0 (the "Terminal" channel, what `SEGGER_RTT_printf` / `SEGGER_RTT_Read` use by default). A different channel can be selected via the **RTT channel** field in Connection Settings (0–15). Under the hood, NinjaTerm sends SEGGER's telnet config string `$$SEGGER_TELNET_ConfigStr=RTTCh;N$$` immediately after the TCP connect so J-Link's server forwards the requested channel. See [SEGGER's J-Link RTT TELNET Channel docs](https://kb.segger.com/J-Link_RTT_TELNET_Channel) for details.

## ANSI Escape Codes

NinjaTerm supports a number of the most popular ANSI escape codes for manipulating the terminal. They are commonly used for coloring/styling text (e.g. making errors red), moving the cursor around and deleting data (e.g. clearing the screen, or re-writing an existing row). These features are very useful when making interactive prompts.

Parsing can be toggled with the ANSI escape code parsing setting in `Settings > RX Settings`. `n` is an optional numeric parameter that defaults to `1` (or `0` for Erase in Display). Sequences that are not in the table below are parsed but otherwise ignored.

| Sequence | Name | Effect |
| --- | --- | --- |
| `ESC[nA` | Cursor Up (CUU) | Move the cursor up `n` rows (won't go above the first row or into scrollback). |
| `ESC[nB` | Cursor Down (CUD) | Move the cursor down `n` rows (won't go past the last row of the screen). |
| `ESC[nC` | Cursor Forward (CUF) | Move the cursor right `n` columns (capped at the terminal width). |
| `ESC[nD` | Cursor Back (CUB) | Move the cursor left `n` columns (capped at column 0). |
| `ESC[r;cH` | Cursor Position (CUP) | Move the cursor to row `r`, column `c` — see below. |
| `ESC[nP` | Delete Character (DCH) | Delete `n` characters at the cursor, shifting the rest of the line left. |
| `ESC[nJ` | Erase in Display (ED) | Clear part of the screen — see below. |
| `ESC[...m` | Select Graphic Rendition (SGR) | Set text color/style — see below. |

### Cursor Position (ESC[r;cH)

`ESC[r;cH` moves the cursor to row `r`, column `c`. Both are 1-based and measured from the top-left of the terminal view, **not** from the start of the scrollback buffer — so `ESC[1;1H` ("home") goes to the top-left of the current screen and the scrollback buffer can never be overwritten.

Either parameter can be left out and defaults to `1`, so `ESC[H`, `ESC[5H` and `ESC[;10H` are all valid. `ESC[r;cf` (Horizontal Vertical Position, HVP) does exactly the same thing. The row is capped at the terminal height and the column at the terminal width (both set in `Settings > Display`). If the terminal doesn't yet hold a full screen of rows, blank rows are added as needed.

Note that the whole sequence has to fit within the max. escape code length set in `Settings > RX Settings` (25 characters by default, which comfortably covers three-digit rows and columns).

:::warning
Turn **timestamps off** when a device positions the cursor. Timestamps are inserted as ordinary characters at the start of each row, so they take up columns your device doesn't know about, and every absolute position lands that far to the left — painting values into the middle of the timestamp instead of where you meant. The "DOS text-mode (CP437)" preset turns them off for you.
:::

### Erase in Display (ESC[nJ)

The current rows in view are ignored when performing Erase in Display commands, as the user could be viewing old data in the scrollback buffer while the cursor is still at the bottom row of data.

`ESC[0J` will clear all data from the cursor position to the end of all data.

`ESC[1J` will clear all data from the last N rows of data, where N is enough rows to completely fill the view port (e.g. the number of rows in the terminal, ignoring scrollback) up to where the cursor is. This command has no effect if the cursor is not in these last N rows.

`ESC[2J` (clear entire screen) will insert enough empty, blank rows into the terminal such that the cursor would be at the top right of the view port with a "blank screen" if the user was not looking in the scrollback.

`ESC[3J` (clear all data from terminal and scrollback buffer) will delete all data in the terminal and the scrollback buffer. This is the same as pressing the clear button in the terminal view.

### Select Graphic Rendition (ESC[...m)

Sets the text style for subsequent characters. Multiple codes can be combined, separated by `;` (e.g. `ESC[1;31m` for bold red). The supported codes are:

- `0` — reset all styles (also the default when no code is given, i.e. `ESC[m`)
- `1` — bold / increased intensity
- `30`–`37` — foreground color, `90`–`97` — bright foreground color
- `40`–`47` — background color, `100`–`107` — bright background color

These can override the default background/TX/RX colors set in `Settings > Display`.

## Timestamps

You can enable timestamps for received data, which will appear at the start of each new line. This feature is available in `Settings > RX Settings`.

The format of the timestamp is customizable, with a number of common formats predefined, as well as the ability to enter a custom format.

## Sending Data (TX Mode)

`Settings > TX Settings > TX Mode` controls when what you type is actually sent.

**Character** (the default) sends each keystroke the moment you press it, which is how a
traditional terminal behaves. This is what you want when you are talking to something with a
shell or command-line interface, where the device echoes characters back and handles its own
line editing.

**Line** buffers what you type into a bar below the terminal and sends the whole line as a
single write when you press Enter. Press Up and Down in the bar to recall previously sent
lines, and Escape to clear it.

Line mode matters for more than convenience. In character mode each keystroke is a separate
write, and over a TCP socket that means a separate segment per character — typing `*IDN?` and
pressing Enter puts six segments on the wire. Devices that expect one command per datagram,
most commonly SCPI instruments over TCP, will ignore a command that arrives split up like
that. Line mode sends it in one piece.

The line terminator is still whatever you have chosen under `When enter is pressed`, so line
mode and character mode agree on what ends a line.

## Other Terminal Features

### Copy and Paste

#### Copying Text

Each terminal window has a "Copy all text" button, allowing you to quickly copy the entire content of that terminal, including its scrollback buffer, to your clipboard.

You can also select text and copy it with `Ctrl+C` (or `Ctrl+Shift+C`). By default, `Ctrl+C` uses smart copy/paste mode (matching the behavior of Windows Terminal and iTerm2):

- If text is selected, `Ctrl+C` copies it to the clipboard and clears the selection.
- If no text is selected, `Ctrl+C` sends the 0x03 control code to the serial port as normal (requires _Send 0x01-0x1A when Ctrl+A thru Ctrl+Z is pressed_ to also be enabled in TX Settings).

`Ctrl+Shift+C` always copies selected text to the clipboard regardless of this setting.

#### Pasting Text

`Ctrl+V` (or `Ctrl+Shift+V`) pastes text from the clipboard to the serial port. In smart copy/paste mode (default), `Ctrl+V` always pastes; with the setting disabled, use `Ctrl+Shift+V`.

#### Configuring Copy/Paste Behavior

The smart `Ctrl+C`/`Ctrl+V` behavior can be toggled in `Settings > TX > Meta Keys` via the _Use Ctrl+C/V for copy/paste_ checkbox. Disable it if you need `Ctrl+C` and `Ctrl+V` to always send raw control codes (0x03 and 0x16).

### Auto Scroll Lock on TX

By default, if you enter TX data into a terminal it will jump to the bottom of the terminal and lock the scroll. You can disable this in `Settings > Display`.

### Customizable Default Background, TX Text, and RX Text Colors

Tailor your terminal's appearance by setting default colors for the background, TX (transmitted) text, and RX (received) text. Find these options in `Settings > Display`. Note that ANSI escape codes for colors can override these defaults if ANSI escape code parsing is enabled.

### Character Encoding

The character encoding of received data — how the incoming bytes are turned into the characters you see — is set in `Settings > RX Settings`:

| Option | Description |
| --- | --- |
| ASCII only (default) | 7-bit ASCII. Bytes `0x80`+ aren't text, so they're shown as hex glyphs (or swallowed) per the non-visible character setting. Best for general debugging, where the raw byte value is what matters. |
| UTF-8 | Decode bytes `0x80`+ as UTF-8. Characters split across separate reads from the port are handled. Bytes that aren't valid UTF-8 fall back to hex glyphs so they stay visible. |
| CP437 (DOS) | Decode bytes `0x80`+ as code page 437, the original IBM PC / MS-DOS character set. |

All three agree on the bytes below `0x80` — control characters below `0x20`, printable ASCII from `0x20` to `0x7E` — so in practice the choice only changes what the bytes from `0x80` up mean.

CP437 is the one to pick for DOS-style text-mode output, where a single byte is a single box-drawing character — e.g. byte `0xDA` is `┌` and `0xC4` is `─`. Devices that send UTF-8 (three bytes per box-drawing character) want the UTF-8 option instead.

Which to use is really a question about your firmware's source file, not your device. If your toolchain saves source as UTF-8 (STM32CubeIDE does, for example) you have two options:

- Pick **UTF-8** in NinjaTerm and write the box-drawing characters directly in your source: `printf("┌───┐")`. The compiler encodes them as UTF-8 and NinjaTerm decodes them back.
- Pick **CP437** and emit the raw bytes with hex escapes: `printf("\xDA\xC4\xC4\xC4\xBF")`. More faithful to a real DOS device, but harder to read in the source.


This setting decides how bytes are *decoded*; the Terminal Font setting below decides whether the resulting characters have glyphs to draw with. You need both for text-mode frames to display.

### Terminal Font

The font used to display data in the terminal can be changed in `Settings > Display`:

| Option | Description |
| --- | --- |
| NinjaTerm (default) | NinjaTerm's own font. Covers ASCII only. |
| IBM VGA (DOS/CP437) | The bundled IBM VGA 8x16 DOS text-mode font. Covers the CP437 box-drawing and block characters, so text-mode frames and borders drawn with `─│┌┐└┘├┤` render properly. |
| Perfect DOS VGA 437 | The bundled Perfect DOS VGA 437 font, another DOS text-mode font that also covers the CP437 box-drawing characters. |

:::tip
Both DOS fonts are bitmap fonts whose glyphs fill their cell exactly, so set **Vertical Row Padding** to `0` when you use one. Any padding leaves a gap between rows, and the vertical strokes of a box-drawing frame stop joining up. The "DOS text-mode (CP437)" preset does this for you. NinjaTerm's own font has built-in spacing and looks better with a few pixels of padding.
:::
| System monospace | Whatever monospace font your operating system provides (Consolas, Menlo, DejaVu Sans Mono, ...). |
| Custom... | Any monospace font already installed on your computer, named in the "Custom Font Family" box that appears — e.g. `Perfect DOS VGA 437`. |

Characters missing from the selected font fall back to a system monospace font, so the terminal's character grid always stays aligned. Combined with the cursor positioning escape codes above, this is what makes full-screen text-mode user interfaces display correctly.

The bundled IBM VGA font is from [The Ultimate Oldschool PC Font Pack](https://int10h.org/oldschool-pc-fonts/) by VileR, used under a [CC BY-SA 4.0](http://creativecommons.org/licenses/by-sa/4.0/) license. Perfect DOS VGA 437 is by [Zeh Fernando](https://www.zehfernando.com/), used under the author's own free-redistribution terms.

A "Clear app data and reload app" button in `Settings > General Settings` allows you to easily reset all application data stored in your browser (like profiles and settings) and start fresh.

## Graphing

NinjaTerm provides powerful real-time graphing capabilities for visualizing serial data. The graphing system supports two different approaches:

1. **Simple prefix-based parsing**: Character sequences to trigger data extraction for the input data can be specified in the graphing settings.
2. **An advanced ASCII text command-based protocol** for complex multi-plot scenarios: Special commands like `$NT:GPH:ADD_FIG ...` and `$NT:GPH:ADD_DATA ...` can be sent from the other end of the serial connection to create and update plots in NinjaTerm.

Both approaches are text based (ASCII encoded data), and require a character sequence to denote the end of a frame, which triggers the graphing system to look for data in the buffer since the last end of frame character. This defaults to the `LF` character (0x0A), which is normally suitable when intermixing the data with other text such as log messages. The processing trigger sequence is also needed to make sure the buffer is cleared at the right point -- we don't want to clear the buffer half way through receiving graph data.

### Prefix Based Graphing

This is the simplest approach. Enable graphing in the Graphing tab and configure prefixes to extract data from your serial stream. For example, with `y=` as the Y variable prefix, data like `y=25.6` will be plotted.

For example, your MCU might be outputting temperature data every second, intermixed with other log messages like this (line endings are LF):

```
2025-08-12 12:00:00 - MCU has booted. Firmware version 1.0.0.
2025-08-12 12:00:01 - Starting temperature measurements...
2025-08-12 12:00:02 - Temperature: 26.1 degC
2025-08-12 12:00:03 - Temperature: 25.9 degC
2025-08-12 12:00:04 - Some other message...
2025-08-12 12:00:05 - Temperature: 26.0 degC
2025-08-12 12:00:06 - Temperature: 26.3 degC
2025-08-12 12:00:07 - Temperature: 26.1 degC
```

You can configure NinjaTerm to extract the temperature data from the serial stream with the following settings on the Graphing view:

- "Processing Trigger" to "LF (\n)" (this is the default)
- "X Variable Source" to "Received Time"
- "Y Variable Prefix" to "Temperature:"
- "Y Variable Suffix" to "degC"

The result will be a graph of the temperature data over time.

You can also configure the graphing settings to use a different delimiter, or to use a different variable source (e.g. a counter or a timestamp).

### Command Based Graphing

For advanced applications, NinjaTerm supports a command-based graphing protocol that enables multiple plots, multiple traces per plot, and flexible data handling. This is useful when you want to give the MCU (or other device) control over the graphing UI.

The commands are explained below.

#### Graph Management Commands

All graphing related commands start with `$NT:GPH:`. The command does not need be at the start of a graphing frame (i.e. random data can occur before the `$NT:GPH:` command). In Advanced Cmd Mode, NinjaTerm starts buffering when `$NT` is seen and processes the command when a `;` is received that is not inside double quotes.

This is what the commands look like:

```
// Create a figure
$NT:GPH:ADD_FIG,id=fig1,title="Voltage Monitoring",xlabel="Time [s]",ylabel="Voltage [V]";

// Add a trace to the figure
$NT:GPH:ADD_TRACE,fig=fig1,id=temp,name="Temperature (°C)",color=#FF4444,xtype=timestamp;

// Add data to the trace
$NT:GPH:ADD_DATA,trace=temp,data=[25.6,26.1,25.9];
```

All `GPH` commands must always be terminated with an unescaped `;` character. Commands start with `$NT:GPH:` and end with `;`. You can send multiple commands in sequence, each properly terminated. If a semicolon appears inside double quotes (e.g., in a title), it is treated as part of the string and not a terminator.

#### GPH:ADD_FIG

Add a new figure to the graphing area in NinjaTerm with the `$NT:GPH:ADD_FIG` command. Graphs are stacked vertically in the graphing area.

```
$NT:GPH:ADD_FIG,id=fig1,title="My Title",xlabel="Time [s]",ylabel="Voltage [V]";
```

The `$NT:GPH:ADD_FIG` command supports the following parameters:

| Property | Required? | Description |
|----------|-----------|-------------|
| `id` | Required | Unique identifier for the plot |
| `title` | Optional | Plot title displayed above the graph. Defaults to the plot ID if not specified |
| `xlabel` | Optional | Custom label for the X-axis. Defaults to "X Axis" if not specified. Example: `xlabel="Time [s]"` |
| `ylabel` | Optional | Custom label for the Y-axis. Defaults to "Y Axis" if not specified. Example: `ylabel="Voltage [V]"` |

Parameter values containing spaces or special characters should be enclosed in double quotes.

Do not use non-ASCII characters in the commands as NinjaTerm does not support Unicode encodings such as UTF-8! For example, don't use the Omega symbol for the units of resistance in the axis labels!

#### GPH:ADD_TRACE

A trace is a individual data series on a plot. Traces need to be created before data can be added to them.

Create a new trace on a plot with the `$NT:GPH:ADD_TRACE` command. A trace needs to be assigned to an existing plot.

```
$NT:GPH:ADD_TRACE,fig=fig1,id=temp,name="Temperature",color=#FF0000,xtype=timestamp;
```

The `$NT:GPH:ADD_TRACE` command supports the following parameters:

| Property | Required? | Description |
|----------|-----------|-------------|
| `fig` | Required | The ID of the figure that this trace will be added to. The figure must have been created prior with the `GPH:ADD_FIG` command. |
| `id` | Required | Unique identifier for the trace. A trace must have a unique ID not just within its figure, but also across all figures. This is so that you don't have to specify both the figure ID and trace ID when adding data to a trace (keeps the serial bandwidth requirements down). |
| `name` | Optional | The name to use in the legend for this trace. Defaults to the trace ID if not specified. |
| `color` | Optional | Set the trace color, both for dots that indicate the data points and the line that joins them. It is a hex code, e.g. `#FF0000` for red. Transparency is also supported by adding the alpha value as another 2-digit hex value at the end. 00 is fully transparent, FF is fully opaque. e.g. `#FF000080` for a 50% transparent red. Transparency can be useful when you have multiple overlapping traces on a single plot. |
| `xtype` | Optional | The type of data to use for the x-axis. There are three options: **timestamp**: The x-axis will be the time data arrived at NinjaTerm. In the `GPH:ADD_DATA` command you supply y-values only. Works well when you a slowly sending single values back per `GPH:ADD_DATA` command (e.g. reading a temperature sensor once per second). **counter**: The x-axis will be a counter that automatically increments (0, 1, 2, ...) for each received data point for that trace. In the `GPH:ADD_DATA` command you supply the y-values only. Works well for arrays of data where each point has been sampled at a regular interval (e.g. an ADC taking 1024 samples and returning all the data in a single `GPH:ADD_DATA` command). **data**: The x-axis will be the data itself. In this case you have to provide both the x and y values in the `GPH:ADD_DATA` command. Works well for scatter plot style data. |

#### GPH:ADD_DATA

Once you have created a plot and a trace on the plot, use the `$NT:GPH:ADD_DATA` command to add data points to the trace. This will draw the points on the graph. For example:

```
$NT:GPH:ADD_DATA,trace=temp,data=[1.23,4.56,7.89];
```

The `$NT:GPH:ADD_DATA` command supports the following parameters:

| Property | Required? | Description |
|----------|-----------|-------------|
| `trace` | Required | The ID of the trace to add the data to. The trace must have been created prior with the `$NT:GPH:ADD_TRACE` command. |
| `data` | Required | The data to add to the trace. This is an array of values. There are two different syntaxes for the data array: **For y-only data** (X values are either counters or timestamps calculated by NinjaTerm): `data=[1.23,4.56,7.89]` **For x,y data pairs**: Use the comma to separate the x and y values, and the pipe to separate the data points. For example: `data=[1,2\|3,4\|5,6]` The array can contain single values. More on this below. |

##### 1. X-Axis Type: timestamp (arrival time)

Use when you want x values to be the time data arrives at NinjaTerm. This works best when you are sending single values over per `$NT:GPH:ADD_DATA` command, such as temperature sensor samples once per second.

```
$NT:GPH:ADD_DATA,trace=temp,data=[1.23];
```

You are allowed to send an extra comma after the last data value (IMO all data formats should allow this, I'm looking at you, JSON and C++ initializer lists!), so you don't have to add conditional logic in your firmware to not generate the comma on the last data value.

You can send multiple values over at once with `timestamp`, but I don't see this as being very useful as they will all get the same timestamp (e.g. all have the same x-axis value):

```
$NT:GPH:ADD_DATA,trace=temp,data=[1.25,1.28,1.31];
```

Remember that the timestamp is the time the data is received by NinjaTerm. Due to buffering, processing time and other work your computer might be doing, this timestamp might be quite different to the time the data was measured. If you need more accurate time stamping (e.g. better than 10-100ms resolution), timestamp the data on the microcontroller and use `xtype=data` instead, bundling the timestamp as the x value.

##### 2. X-Axis Type: counter (auto-incrementing)

Use when you want x values to automatically increment (0, 1, 2, ...):

```
$NT:GPH:ADD_DATA,trace=accel,data=[9.82,9.85,9.79,9.83];
```

##### 3. X-Axis Type: data (x,y pairs)

As mentioned above, if you have set the xtype to data then you have to provide (x, y) data pairs in this command. Separate the x and y values with a comma (`,`), and separate (x,y) pairs from one another with a pipe (`|`). For example:

```
$NT:GPH:ADD_DATA,trace=position,data=[124.45,26.1|125.45,26.8|126.45,27.2];
```

#### Complete Example

Here's a complete example showing how to create a multi-trace plot with custom axis labels:

```
// Create a plot for sensor data with custom axis labels
$NT:GPH:ADD_FIG,id=sensors,title="Environmental Sensors",xlabel="Time [s]",ylabel="Sensor Value";

// Create traces for different sensor types
$NT:GPH:ADD_TRACE,fig=sensors,id=temp,name="Temperature (°C)",color=#FF4444,xtype=timestamp;
$NT:GPH:ADD_TRACE,fig=sensors,id=humidity,name="Humidity (%)",color=#4444FF,xtype=timestamp;
$NT:GPH:ADD_TRACE,fig=sensors,id=pressure,name="Pressure (hPa)",color=#44FF44,xtype=timestamp;

// Send data (your firmware would send these)
$NT:GPH:ADD_DATA,trace=temp,data=25.6;
$NT:GPH:ADD_DATA,trace=humidity,data=67.2;
$NT:GPH:ADD_DATA,trace=pressure,data=1013.25;

// Send more data points
$NT:GPH:ADD_DATA,trace=temp,data=[25.8,26.1,25.9];
$NT:GPH:ADD_DATA,trace=humidity,data=[68.1,67.8,69.2];
$NT:GPH:ADD_DATA,trace=pressure,data=[1013.1,1012.9,1013.3];
```

#### Clearing and Deleting

NinjaTerm provides a number of way of clearing and deleting figures and traces. This is useful for a number of reasons, such as:

- Clearing everything when the MCU starts up to start fresh on reset.
- Updating a figure without appending, i.e. if you take many samples of something at once, and want to refresh the old samples with the new samples.

##### Clearing a Figure

Use the command `$NT:GPH:CLR_FIG` to clear all data from a plot. This will leave the figure on the screen (i.e. it won't delete the figure), but will delete all traces from it. Here is an example:

```
$NT:GPH:CLR_FIG,fig=fig1;
```

The `$NT:GPH:CLR_FIG` command supports the following parameters:

| Property | Required? | Description |
|----------|-----------|-------------|
| `fig` | Required | The figure ID to clear all data from. |

##### Deleting a Figure

Use the command `$NT:GPH:DEL_FIG` to delete a figure. This will delete the figure (remove it from the screen) and all traces from it. Here is an example:

```
$NT:GPH:DEL_FIG,fig=fig1;
```

The `$NT:GPH:DEL_FIG` command supports the following parameters:

| Property | Required? | Description |
|----------|-----------|-------------|
| `fig` | Required | The figure ID to delete. |

##### Deleting a Trace

Use the command `$NT:GPH:DEL_TRACE` to delete a trace. This will delete the trace from the figure it is added to. Here is an example:

```
$NT:GPH:DEL_TRACE,trace=temp;
```

The `$NT:GPH:DEL_TRACE` command supports the following parameters:

| Property | Required? | Description |
|----------|-----------|-------------|
| `trace` | Required | The trace ID to delete. |

#### Data Array Syntax

When providing multiple data points in a single `GPH:ADD_DATA` command, you must enclose the comma-separated values in square brackets. This prevents confusion between parameter separators and data separators.

**Examples:**
- Single value: `data=25.6`
- Multiple values: `data=[25.6,26.1,25.9]`
- Invalid (old syntax): `data=25.6,26.1,25.9` - this won't work because the commas are interpreted as parameter separators

#### Command Protocol Notes

- Commands must start with `$NT:GPH:` and end with an unquoted `;`
- In Advanced Cmd Mode, NinjaTerm buffers from `$NT` until a `;` that is not inside quotes and processes that as a command
- In Basic Prefix Mode, `$NT:GPH:` commands are processed when the configured processing trigger (e.g., LF) is received
- Parameters are comma-separated key=value pairs
- Color values can be hex codes (e.g., `#FF0000`) or standard color names
- Trace IDs must be unique within their plot context
- Multiple data points in a single ADD_DATA command can be separated by pipes (for x,y pairs) or commas (for y-only values)

#### Enhanced Data Examples

Example showing the new syntax with multiple x,y data pairs separated by pipes:

```
// Example with multiple x,y data pairs using pipe separator
$NT:GPH:ADD_DATA,trace=temp,data=1,25|2,16|3,18;

// Complete workflow example
$NT:GPH:ADD_FIG,id=sensors,title="Temperature Log";
$NT:GPH:ADD_TRACE,fig=sensors,id=temp,xtype=data,name="Temperature",color=#FF0000;
$NT:GPH:ADD_DATA,trace=temp,data=1,25|2,26|3,18|4,22|5,20;
```

## AI Integration (MCP Server)

NinjaTerm includes a built-in [MCP (Model Context Protocol)](https://modelcontextprotocol.io) server that lets AI coding assistants — such as Claude Code, Cursor, and Copilot — read serial output and send commands directly, without copy-pasting between windows.

### Enabling the MCP Server

1. Open `Settings > General`
2. Check **Enable MCP server**
3. Optionally change the port (default: `3579`)

When enabled, the status bar at the bottom of the window shows **MCP ON** (green). Clicking it jumps back to the General settings page.

### Connecting an AI Client

Once the server is running, register it with your AI tool.

**Claude Code:**

```bash
claude mcp add --transport http ninjaterm http://127.0.0.1:3579/mcp
```

**Cursor** — add the following to `~/.cursor/mcp.json` (global) or `.cursor/mcp.json` (project-specific):

```json
{
  "mcpServers": {
    "ninjaterm": {
      "type": "streamable-http",
      "url": "http://127.0.0.1:3579/mcp"
    }
  }
}
```

**GitHub Copilot (VS Code)** — add the following to `.vscode/mcp.json` in your workspace (or run `MCP: Open Workspace Folder Configuration` from the VS Code command palette):

```json
{
  "servers": {
    "ninjaterm": {
      "type": "http",
      "url": "http://127.0.0.1:3579/mcp"
    }
  }
}
```

**OpenAI (ChatGPT)** — OpenAI's MCP support currently requires a publicly accessible HTTPS endpoint and is not compatible with NinjaTerm's local-only server.

The server only accepts connections from `127.0.0.1` (this machine), so it is not accessible from other devices on your network.

### Available Tools

| Tool | Description |
|---|---|
| `get_terminal_output` | Returns the last N lines of received serial data as plain text. Good for reading historical output or taking a snapshot after sending a command. |
| `send_data` | Sends a string to the currently open serial port. Appends a newline by default (configurable). |
| `get_connection_status` | Returns the current port path, baud rate, and connection state. |
| `list_available_ports` | Lists serial ports visible to the operating system. |

### Streaming Resource

For real-time monitoring, subscribe to the `ninjaterm://terminal/rxstream` resource instead of polling `get_terminal_output`:

| Scenario | Recommended approach |
|---|---|
| Read output that arrived before connecting | `get_terminal_output` tool |
| React to data as it arrives | Subscribe to `ninjaterm://terminal/rxstream` |
| One-shot snapshot after sending a command | `get_terminal_output` with a `lines` count |

When the AI client subscribes, NinjaTerm sends a `notifications/resources/updated` push notification whenever new serial data arrives. The client then reads the resource to retrieve all data buffered since the last read — the buffer is cleared on each read.

### Example Workflow

With a microcontroller connected and NinjaTerm open, you can ask your AI assistant things like:

- *"Work out why the MCU crashed based on the recent serial logs"* → the AI calls `get_terminal_output` to retrieve the last N lines and analyses them for error messages, stack traces, or fault indicators
- *"Send the 'motor on' command via the serial port and verify by the returned log messages that the motor turned on successfully"* → the AI calls `send_data` to send the command, then calls `get_terminal_output` to check the response and confirm the expected log messages appeared
- *"Build and flash the firmware using the connected J-Link, then verify the new feature is working"* → the AI subscribes to `ninjaterm://terminal/rxstream`, runs the build and flash commands (e.g. `cmake`, `ninja`, `JLinkExe`), then watches the incoming serial output to confirm the expected behaviour appears — all in one uninterrupted agentic loop

### Why Use NinjaTerm Instead of Connecting Directly?

You might wonder why an AI assistant can't just open the serial port itself using Python or Node.js. NinjaTerm stays in the loop for several good reasons:

- **Human visibility** — You watch the serial output in real time as the AI works. If something looks wrong you can intervene immediately, rather than waiting for the AI to report back.
- **No port conflicts** — Serial ports can only be opened by one process at a time. NinjaTerm holds the connection; the AI reads data through the MCP bridge without competing for the port.
- **Zero serial configuration for the AI** — The AI doesn't need to know the COM port name, baud rate, parity, or stop bits, and doesn't need to handle platform differences in serial libraries. NinjaTerm already has the connection open and configured.
- **Full scrollback history** — Data that arrived before the AI connected is still accessible via `get_terminal_output`, because NinjaTerm maintains a scrollback buffer. A script started fresh would miss everything that came before it.
- **Your workflow stays the same** — If you already have NinjaTerm open during development, AI assistance is purely additive. There's nothing extra to set up and nothing to tear down when you want to go back to working manually.
